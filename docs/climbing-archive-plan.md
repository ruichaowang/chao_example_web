# 岩馆空间档案：项目计划（草案）

更新：2026-09-29

## 目标

建立可按岩馆和采集时间浏览的空间档案。每次采集形成一个不可覆盖的 Snapshot，记录岩馆空间与线路在不同时期的状态。第一版先验证“找得到岩馆、切得动时间、看得见模型”的完整体验；后续再增加墙面、线路和岩点的空间标注与跨期比较。

这份文档是项目方向和原型约束，不代表当前仓库已经实现以下功能。当前仓库仍是 VitePress / GitHub Pages 示例。

## 对象与关系

- **Gym**：一家具体岩馆或分店，使用稳定 ID、名称、城市、地址等信息。
- **Snapshot**：一次有明确采集日期的空间记录，属于一个 Gym；保留采集方式、模型版本、覆盖范围与质量说明。相同岩馆不同日期不覆盖旧数据。
- **Wall**：Snapshot 中可辨认的一面墙或区域。V1 可只记录名称，直到有可靠的坐标和边界再加入几何信息。
- **Route**：附着于某个 Wall 和 Snapshot 的线路，记录当期颜色、难度、状态与备注。V1 可选填；不假定跨期线路 ID 稳定。

模型是 Snapshot 的资产，一个 Snapshot 可以有多个视角、格式或分辨率。元数据与资产 URL 分开；不把显示格式当作原始档案格式。

## V0 / V1：可使用的空间档案

1. 首页展示岩馆列表，至少可按城市筛选。
2. 岩馆页按采集日期显示 Snapshot 时间轴；清楚标注采集日期与模型覆盖区域。
3. Snapshot 页提供 3D 模型入口、采集说明与已知限制；模型不可用时仍能阅读档案信息。
4. 第一批只录入真实采集的 1 家岩馆、1～2 个 Snapshot，验证手机与桌面端模型加载、交互和维护成本。

验收标准：一个新访客可以在三步内找到某次采集并打开真实模型；新增一次 Snapshot 只需新增元数据和上传资产，不复制整个网页；移动端能正确加载或明确提示失败。

## V2：空间数据与比较

- 建立同一岩馆的稳定坐标参考、墙面 ID 和采集对齐记录；对齐质量必须显式记录，不能仅凭外观假设吻合。
- 支持墙面与线路标注、岩点坐标和证据照片；标注应指向具体 Snapshot 和模型版本。
- 在具备足够真实采集数据后，尝试跨期叠加、增删变化与线路比较。自动识别是研究方向，不承诺第一期实现。

## 技术分层与存储

| 内容 | 初步位置 | 原则 |
| --- | --- | --- |
| 计划、网页源码、元数据 Schema | 本 GitHub 仓库 | GitHub 是正式工程的版本来源 |
| 原型页面与交互 | ChatGPT Sites 探索站点 | 先验证信息架构；原型变更同步回本计划 |
| 正式网页部署 | 待原型验证后选择（如 Cloudflare Pages） | 部署位置不绑定模型存储 |
| 公网展示资产 | 对象存储候选：Cloudflare R2 | 存模型、封面；按 URL 加载，评估费用、CORS 与访问速度 |
| 原始视频、训练输出 | 本地/NAS 或另行备份 | 与公网交付文件分离，制定备份策略 |

V1 拟使用 SuperSplat Viewer / PlayCanvas 加载 Gaussian Splat 展示资产；实际选择前，用自己的模型验证导出格式（如 SOG）、体积、加载速度、手机兼容性及跨域配置。GLB/Mesh 另行验证其展示方式。不把“编辑器能导入”直接等同于“网页 Viewer 能加载”。模型 URL 先用占位值，取得真实公开地址后再接入；不把大模型文件提交进 Git。

建议初始目录（正式实现时再创建）：`src/` 网页与 Viewer、`data/` 岩馆和快照元数据、`public/` 少量缩略图、`docs/` 决策与采集规范。对象存储按 `gym-id/snapshot-date/asset-version/` 组织，避免重建覆盖旧文件。

## Sites 原型要回答的问题

1. 首屏是岩馆列表还是最近更新？城市筛选是否必要？
2. 岩馆页如何呈现时间轴及各次采集的覆盖范围？
3. Snapshot 页的模型、照片、墙面/线路列表、采集说明各占多少空间？
4. 模型无法加载、尚未上传或只有照片时，页面如何工作？
5. 手机浏览时是否仍能轻松切换 Snapshot 和查看模型？

原型使用明确标记的示例数据，不展示虚构模型为真实采集。先做可点击的 Gym → Snapshot 流程与 Viewer 容器；取得真实模型 URL 后再测试集成。原型确定的信息架构与文案需回写本仓库，然后决定是否在此仓库实现正式前端，避免长期维护两套独立代码。
